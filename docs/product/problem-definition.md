# 문제 정의와 샘플 요구사항

## 문제

AI·개발 정보를 자주 확인하는 사용자는 발견, 중복 제거, 처리 상태 기억, 프로젝트 적용을 서로 다른 도구에서 수행한다. 그 결과 중요한 원문을 발견해도 “내 일에 왜 중요한지”를 다시 판단하고 AI에게 같은 맥락을 반복 설명해야 한다.

이번 샘플은 정보 수집기의 완성도가 아니라, **원문 한 건이 사람의 판단을 거쳐 프로젝트 지식으로 전환되는 흐름**이 가치 있는지 검증한다.

## 목표

- 6개의 새 항목에서 오늘 볼 3개가 추려지는 이유를 사용자가 10초 안에 설명할 수 있다.
- 사용자가 한 항목을 열고 프로젝트 관련성, 근거, 제안 행동을 확인할 수 있다.
- 저장, 프로젝트 연결, 숨김이 서로 다른 의미로 이해된다.
- AI의 지식 제안을 사람이 수락하거나 거절하며, 결정 결과가 명확히 보인다.
- AI의 검토가 사람의 읽음 상태를 바꾸지 않음을 데모에서 증명한다.

## 비목표

- 범용 뉴스/소셜 미디어 수집: 신뢰 가능한 공식 RSS/Atom과 mock만 다룬다.
- 완전 자동 개인화: 초기 랭킹 규칙은 설명 가능하고 고정적이어도 된다.
- 모델 재학습: 승인된 지식의 저장·검색 가능성만 설계한다.
- 팀 지식 관리, 결제, 모바일 앱, 알림: 핵심 루프와 무관하다.
- production 인증, 고가용성, 대규모 ingestion: 이벤트용 검증 이후 결정한다.
- AI가 사용자 승인 없이 프로젝트나 외부 agent 상태를 변경하는 기능.

## 핵심 사용자 이야기(P0)

1. AI 기술 변화를 추적하는 개발자로서, 오늘 볼 항목만 받고 싶다. 그래야 탐색 시간을 줄일 수 있다.
2. 프로젝트를 진행하는 개발자로서, 원문이 내 프로젝트에 왜 관련 있는지 근거와 함께 보고 싶다. 그래야 읽을 우선순위를 판단할 수 있다.
3. 사용자로서, 항목을 저장·연결·숨김 중 하나로 처리하고 싶다. 그래야 처리 의도가 섞이지 않는다.
4. 사용자로서, AI가 만든 지식 후보를 수락하거나 거절하고 싶다. 그래야 내 AI가 근거 없는 내용을 사실로 사용하지 않는다.
5. 사용자로서, AI가 검토한 항목과 내가 읽은 항목을 따로 보고 싶다. 그래야 내 처리 상태를 잃지 않는다.

## 샘플 수락 기준

- Given 6개의 수집 항목과 1개의 프로젝트가 있을 때, When Today를 열면, Then 3개의 우선 항목과 선택 이유가 보인다.
- Given 사용자가 읽지 않은 항목을 agent가 검토했을 때, When 목록을 다시 보면, Then 사람 상태는 `unread`, agent 상태는 `reviewed`다.
- Given 항목이 프로젝트와 관련 있을 때, When 상세를 열면, Then 관련도와 2개 이상의 근거가 원문 인용 없이 요약되어 보인다.
- Given AI가 지식 후보를 제안했을 때, When 사용자가 수락하면, Then 승인된 지식과 출처, 프로젝트 연결이 생성된다.
- Given 같은 제안을 거절했을 때, Then 지식은 생성되지 않고 거절 결정만 남는다.
- Given 사용자가 항목을 숨겼을 때, Then Today에서 사라지지만 원문과 audit record는 삭제되지 않는다.

## 성공 판정

정량 지표를 제품 성과로 과장하지 않고 5명 내외의 데모 관찰로 다음을 확인한다.

- 4명 이상이 제품을 “AI 뉴스 요약”이 아니라 “내 프로젝트와 AI에 정보를 연결하는 도구”로 설명한다.
- 4명 이상이 `저장`과 `AI에게 학습`의 차이를 설명한다.
- 5명 모두 agent의 검토와 사람의 읽음이 별개여야 한다고 답한다.
- 핵심 흐름을 진행자가 개입하지 않고 90초 안에 완료한다.
